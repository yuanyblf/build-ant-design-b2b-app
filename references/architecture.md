# 应用架构规范

## 基本原则

- 优先按业务功能组织代码，再在功能内部划分技术目录。
- 依赖方向保持为 `app → features → shared`，禁止 `shared` 反向依赖业务功能。
- 尽量将领域规则写成纯函数，并在不渲染界面的情况下测试。
- 应用外壳只负责导航、Provider、登录态、全局异常处理和路由组合。
- 统一处理 API 传输、认证头、错误标准化和请求追踪编号。

## 统一应用骨架

采用 Ant Design 原生 `Layout` 组合，不自行实现已有的布局和菜单能力：

```text
┌──────────────────────────────────────────────────────────┐
│ Logo        应用切换（常用应用／全部应用）     当前用户 │
├──────────────┬───────────────────────────────────────────┤
│ 应用菜单     │ 面包屑／页面标题／页面操作                 │
│  └ 二级菜单  │                                           │
│              │ 功能区                                    │
└──────────────┴───────────────────────────────────────────┘
```

- 顶部 `Header` 始终通栏。Logo 在左、“应用”切换区在中、当前用户和全局操作在右；顶部应用不计入菜单层级。
- 主体使用 `Sider + Content`。`Sider` 展示当前应用的应用菜单，有子菜单时用 `SubMenu` 展开第二级。
- `Header` 与 `Sider/Menu` 必须同时支持浅色和深色模式；业务提示未明确要求深色时使用浅色模式。模式值从 `theme.navigation` 读取，不在应用外壳中硬编码背景色、文字色或 Menu theme。
- `Sider` 不设置应用标题区，应用菜单从侧栏顶部直接开始；当前应用由顶部应用切换区和页面面包屑表达。
- 应用菜单最多两级。更深层级使用页面内页签、分区或面包屑表达。
- 切换应用后同步替换左侧应用菜单、进入该应用默认路由并更新面包屑。页面刷新后应根据当前路由恢复应用与菜单选中状态。
- 常用应用直接显示，默认最多 4 个。更多应用通过“全部应用”入口收缩，并按业务分类在悬浮卡片中展示；同时保留点击打开能力，便于触控和键盘操作。卡片中的应用项包含图标和名称。
- 所有可见应用和菜单项都必须配置语义明确的图标；同类状态可以复用一套图标语义。
- 窄屏下使用 Ant Design `Drawer` 承载左侧菜单，顶部保留 Logo、当前应用和用户入口；全部应用卡片改用适应视口的列数。
- 右侧内容区使用流式宽度和统一响应式 Gutter，页面、列表、表格和独立表单默认占满可用空间；不得在业务页面写死整体容器宽度，阅读型内容可按场景限制最大阅读宽度。
- 布局结构作为产品框架约束，不做任意模板切换；颜色、字号、间距、边框、圆角、阴影和组件 Token 由规范配置控制。主交互色使用 `#2A56DE`，辅助色 `#FF6B06` 只用于特殊强调和个别标签。

## 模块边界

使用 `app` 负责应用组合，`features` 负责业务能力，`shared` 负责稳定的公共基础设施。每个业务功能拥有自己的 API 适配、领域模型、界面和路由，仅通过功能目录下的 `index.ts` 暴露确有需要的公共能力。

不要创建混合各种业务概念的全局 `components` 目录。只有当第二个真实业务场景证明组件具有稳定且与业务无关的接口时，才将其提升到 `shared/ui`。

## 数据流

1. 根据后端契约定义传输对象 DTO。
2. 当接口结构与界面模型存在差异时，在 API 边界完成转换。
3. 远程数据缓存放入项目已有的服务端状态管理方案。
4. 可分享、可回访的筛选和分页状态放入 URL。
5. 临时交互状态放在距离使用位置最近的组件中。
6. 能够推导的数据保持推导，不维护重复状态。

## 路由与权限

显式定义路由元数据：路径、标题、面包屑、是否显示在导航、功能开关和所需权限。权限检查至少覆盖：

- 路由层：阻止进入无权访问的模块。
- 操作层：根据场景隐藏或禁用按钮；当解释限制有帮助时优先禁用并说明原因。
- 服务端层：以服务端权限校验为最终依据。

权限使用 `order.read`、`order.approve` 等能力标识，不直接比较岗位名称。有效链接但无权访问时，显示明确的“无权限”状态。

## 错误模型

至少区分：参数校验失败、未登录、无权限、资源不存在、数据冲突、请求限流、网络异常和未知异常。保留请求编号供问题排查。可恢复的业务错误就地展示，意外的渲染错误由全局错误边界处理。

## 测试重点

- 单元测试覆盖状态流转、校验规则、格式化函数和权限判断。
- 集成测试覆盖核心业务路径和提交失败后的恢复行为。
- 高价值或不可逆操作增加端到端测试。
- 测试用户可观察行为，不依赖组件内部实现细节。
