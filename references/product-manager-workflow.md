# 产品经理业务原型工作流

## 工作阶段

面向产品经理时，将一次原型任务拆成四个阶段：

1. 理解业务：提取角色、目标、对象、状态、操作、风险和验收重点。
2. 规划确认：先输出两级应用菜单、页面清单、状态流转、关键字段、交互建议和验证方案，不修改页面。
3. 原型实现：产品经理明确确认后，再生成可运行页面和模拟数据。
4. 结果验证：执行规范校验、构建和浏览器主流程测试，输出“通过、失败、待确认”清单；明确问题可直接修复并复测。

用户明确要求直接实现时可以跳过单独确认，但仍需在实现前内部完成业务契约和页面模式判断。

## 规划输出

规划至少包含：

- 应用定位、使用角色和业务目标。
- 两级以内的应用菜单及默认页面。
- 列表、表单、详情、流程和设置页面清单。
- 核心实体、字段、状态和允许的状态流转。
- 查询、新增、详情、行操作和批量操作。
- 权限、资金、通知、隐私、删除等高风险事项。
- 页面模式选择理由和需要覆盖的组件场景。
- 主流程、异常流程、规范和工程验证方案。

只询问会改变业务行为、权限、不可逆操作或数据契约的问题。视觉和组件细节优先从共享规范推导。

## 原型边界

- 默认使用模拟数据。
- 不连接生产接口，不发送真实消息，不发放真实权益，不执行真实资金或不可逆操作。
- 需要真实外部行为时，先明确环境、权限、数据范围和回滚方式。
- 演示行为必须明确标记为模拟，不能让产品经理误以为真实业务已完成。

## 验证输出

验证结果按以下三类输出：

- 通过：已实际验证且符合业务和共享规范。
- 失败：存在明确问题，说明影响、修复和复测结果。
- 待确认：缺少业务决策、真实接口或权限，不能通过界面假设决定。

至少验证：应用和菜单联动、默认页面、查询、新增、详情、状态操作、必填和联动、危险操作、空／失败状态、按钮顺序、响应式、规范配置、TypeScript 和生产构建。

## 修改分类

- 用户说“作为规范保存到 Skill”时，同步更新默认 JSON、校验脚本、规范参考和代表性 Demo。
- 用户说“只修改当前页面／应用”时，只改业务功能，不改变共享规范。
- 范围不明确时，根据是否适用于未来所有业务页面判断；可能造成广泛变化时先说明判断并请求确认。
