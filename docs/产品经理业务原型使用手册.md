# 产品经理业务原型使用手册

本手册面向产品经理，说明如何使用 `build-ant-design-b2b-app` Skill，把业务想法快速转换为可运行、可评审、可验证的 Ant Design B 端原型。

配置字段、颜色、字号、间距等内容请查看《b2b-standards.json 中文配置指南》。本手册只关注业务原型工作方法。

## 1. Skill 能做什么

产品经理主要描述业务，不需要先决定具体的 Ant Design 组件、页面间距或工程目录。

Skill 可以协助完成：

- 把业务场景拆成应用、菜单、页面和操作流程。
- 建立角色、权限、字段、状态和业务规则。
- 选择列表、卡片、弹窗、抽屉、独立表单、详情页或分步流程。
- 按统一规范生成可运行的 React + TypeScript + Ant Design 原型。
- 使用模拟数据演示查询、新增、编辑、详情、批量操作和状态流转。
- 检查页面规范、业务流程、异常状态、构建结果和浏览器表现。
- 根据评审意见继续修改，并判断修改属于业务需求还是全局规范。

Skill 默认不会连接真实生产接口、发送真实消息、发放真实权益或执行不可逆操作，除非产品经理明确授权并提供对应环境。

## 2. 推荐工作流程

```text
提出业务场景
→ Skill 输出规划建议和待确认事项
→ 产品经理确认范围
→ Skill 生成可运行原型
→ Skill 执行业务与规范验证
→ 产品经理体验并提出修改
→ Skill 更新原型或沉淀全局规范
```

建议把一次需求拆成四个阶段，不要在业务目标尚未确认时直接要求制作全部页面。

### 阶段一：业务理解

产品经理说明用户是谁、要解决什么问题、需要管理什么业务对象，以及最重要的操作。

### 阶段二：方案确认

要求 Skill 先给出应用菜单、页面清单、状态流转、关键字段和交互建议。此阶段不修改代码。

### 阶段三：原型制作

产品经理确认方案后回复“确认，开始制作”，Skill 再生成页面和模拟数据。

### 阶段四：验证迭代

要求 Skill 实际操作 Demo，验证主流程、异常流程和规范符合度，然后根据评审反馈继续调整。

## 3. 第一步：描述业务场景

一个有效的业务描述至少包含以下信息：

| 信息 | 需要说明的内容 | 示例 |
| --- | --- | --- |
| 业务场景 | 要管理的业务是什么 | 企业培训课程运营 |
| 使用角色 | 谁使用这个功能 | 培训管理员、部门负责人 |
| 业务对象 | 管理哪些数据 | 课程、章节、培训计划、学习记录 |
| 核心操作 | 用户要完成什么 | 新建课程、发布课程、查看学习进度 |
| 状态 | 对象如何变化 | 草稿、已发布、已下架 |
| 高风险行为 | 是否涉及资金、通知、隐私或删除 | 发布后通知员工，包含员工学习数据 |
| 期望验证 | 最想通过原型确认什么 | 创建课程是否顺畅、详情信息是否够用 |

不知道的内容可以写“请根据常见 B 端场景建议”，Skill 会先给出假设，不会因为缺少视觉细节而停止。

推荐首次输入：

```text
请使用 build-ant-design-b2b-app Skill 规划一个【业务名称】应用。

业务目标：
使用角色：
主要业务对象：
核心操作：
已知状态：
涉及的高风险行为：
我最希望通过原型验证：

请先理解业务，输出应用菜单、页面清单、关键流程和规划建议。
暂时不要生成页面，等我确认后再制作。
```

## 4. 第二步：先规划再制作

规划阶段建议要求 Skill 输出以下内容：

1. 应用定位和目标用户。
2. 两级以内的应用菜单。
3. 每个菜单对应的默认页面。
4. 列表、表单、详情和设置页面清单。
5. 核心实体与字段。
6. 状态流转和允许执行的操作。
7. 权限、高风险操作和需要确认的业务假设。
8. 原型需要覆盖的组件和交互场景。
9. 后续验证方案。

产品经理评审规划时，重点回答：

- 菜单是否符合实际工作分工？
- 默认进入的页面是否是最高频任务？
- 是否遗漏关键对象或关键状态？
- 哪些操作需要审批、确认或权限控制？
- 原型需要验证完整流程，还是只验证信息结构？
- 模拟数据是否可以使用，是否涉及敏感数据？

确认用语示例：

```text
规划确认，可以开始制作页面。
使用模拟数据，不连接真实接口。
优先实现课程管理、课程详情和培训计划，其他页面先保留菜单入口。
```

## 5. 第三步：生成业务原型

Skill 制作原型时会优先遵守现有 B 端规范：

- 顶部为应用切换，应用较多时进入分类悬浮卡片。
- 左侧直接展示当前应用菜单，最多两级。
- 菜单默认进入列表或集合页面。
- 列表页依次展示面包屑、标题、查询区和结果区。
- 查询区一行最多四项，按钮组也占一项；字段多时自动折叠。
- 主操作按钮位于按钮组最左侧。
- 可进入详情的字段使用链接形式。
- 复杂表单使用独立页面或分步流程。
- 高级详情突出状态、金额、进度等关键指标。

产品经理不需要指定“使用 Card 还是 Table”。如果业务上有明确原因，可以直接说明，例如：

```text
课程需要通过封面帮助管理员识别，请用图文卡片列表。
员工触达记录需要精确比较，请用表格。
创建计划有严格先后顺序，请用分步表单。
```

## 6. 第四步：验证业务结果

生成页面后，不要只检查“页面能否打开”。建议要求 Skill 同时执行四类验证。

### 6.1 业务流程验证

- 能否从应用入口进入正确默认页？
- 查询、新增、详情和返回列表是否连续？
- 状态变化后，可执行操作是否同步变化？
- 批量操作是否只作用于选中对象？
- 高风险操作是否说明对象、数量和影响？

### 6.2 表单验证

- 必填项为空时是否阻止下一步或提交？
- 默认值、数据源、格式和联动是否符合需求？
- 返回上一步是否保留已填写内容？
- 提交失败后输入是否仍然保留？
- 主操作是否在按钮组左侧？

### 6.3 页面规范验证

- 应用菜单是否最多两级？
- 列表页层级和查询区布局是否正确？
- 详情字段是否按一行三列展示？
- 卡片标题是否单行，摘要是否最多两行？
- 高级表单操作栏是否吸底？
- 弹窗、抽屉和详情承载方式是否匹配复杂度？

### 6.4 工程验证

- 规范配置校验是否通过？
- TypeScript 是否编译通过？
- 生产构建是否通过？
- 浏览器中是否存在溢出、遮挡或不可操作控件？
- 是否有非阻塞警告和后续工程建议？

推荐验证指令：

```text
请按产品经理视角验证刚生成的原型：
1. 实际走完主要业务流程；
2. 检查必填、失败、空数据和危险操作；
3. 对照 B 端 Skill 规范检查页面；
4. 运行规范校验和生产构建；
5. 输出“通过、失败、待确认”清单；
6. 发现明确问题时直接修复并复测。
```

## 7. 常用提示词模板

### 7.1 新业务应用规划

```text
使用 B 端 Skill 规划【应用名称】。
目标用户是【角色】，他们需要完成【核心任务】。
主要对象包括【对象列表】，核心状态包括【状态列表】。
请先给出两级菜单、页面清单、状态流转、关键字段和验证方案，不要立即制作页面。
```

### 7.2 确认并生成原型

```text
规划确认，开始生成原型。
本轮实现范围：【页面范围】。
使用模拟数据，不调用真实接口。
必须覆盖：【需要重点验证的交互】。
完成后请进行构建和浏览器验证。
```

### 7.3 增加列表页

```text
在【应用／菜单】下增加【对象】列表。
查询条件：【字段】。
表格字段：【字段】。
主要操作：【操作】。
批量操作：【操作】。
点击【字段】进入详情。
请先补全缺失的默认值、数据源、状态和异常规则，再实现页面。
```

### 7.4 增加表单

```text
增加【新建／编辑】功能，字段包括：【字段】。
其中【字段】必填，【字段】来自【数据源】，选择【字段】后联动【规则】。
提交会产生【影响】。
请根据复杂度决定弹窗、抽屉、独立页面或分步表单，并解释选择原因。
```

### 7.5 增加详情页

```text
增加【对象】详情页。
需要突出显示：【状态／金额／进度】。
详情包含：【基础信息、关联表格、时间线等】。
允许操作：【操作】。
请按基础详情或高级详情规范实现。
```

### 7.6 修改全局规范

```text
这是全局规范修改，不是单个页面修改：
【描述规则】。
请同步更新 b2b-standards.json、校验脚本、中文配置指南、Skill 规范和 Demo 代表页面，并完成复测。
```

### 7.7 只修改当前业务

```text
该调整只适用于【应用／页面】，不要修改全局规范：
【描述调整】。
```

## 8. 页面和交互选择规则

| 业务情况 | 推荐形式 |
| --- | --- |
| 管理一组可查询、可批量处理的数据 | 表格列表 |
| 依赖图片识别内容，如课程、文章、活动 | 紧凑图文卡片列表 |
| 不超过 6 个简单字段 | 弹窗表单 |
| 7～16 个字段，需保留列表上下文 | 抽屉表单 |
| 字段多、分组多、上传或复杂联动 | 独立高级表单 |
| 任务存在严格先后顺序 | 分步表单 |
| 少量字段、单一信息组 | 基础详情 |
| 操作多，需突出状态、金额或进度 | 高级详情 |
| 需要展示上下级关系 | 树形结构 |
| 需要展示完成程度 | 进度条 |
| 需要展示状态变化过程 | 时间线 |

产品经理可以提出业务目标，由 Skill 选择页面形式；只有业务有明确理由时才指定组件。

## 9. 如何提出修改意见

修改意见应尽量包含“范围、问题、期望和是否属于全局规范”。

推荐写法：

```text
范围：人文关怀 > 关怀计划详情。
问题：计划基础信息放在侧栏后不方便横向核对。
期望：移到主内容区，一行三列。
类型：沿用现有详情页全局规范。
```

不推荐只写“这里不好看”“调整一下布局”，因为无法判断问题是业务信息结构还是视觉偏好。

如果一句修改适用于所有应用和未来页面，应明确写“作为全局规范保存到 Skill”。如果只适用于当前场景，应写“不要修改全局规范”。

## 10. 完整示例

### 示例：培训课程

第一轮：

```text
使用 B 端 Skill 规划“培训课程”应用。
用户是培训管理员，需要维护课程、发布培训计划、查看员工学习进度。
课程包含封面、讲师、章节、视频资料和适用范围。
请先规划菜单、页面、状态和验证方案，我确认后再制作。
```

确认后：

```text
规划确认。先制作课程管理卡片列表、课程高级详情、新建课程高级表单和培训计划列表。
使用模拟数据；上传只做交互演示。
完成后验证课程查询、查看详情、必填校验和应用菜单切换。
```

### 示例：人文关怀

第一轮：

```text
使用 B 端 Skill 规划“人文关怀”应用。
管理员需要创建生日、入职周年和节日关怀计划，设置人员、通知内容、权益和执行时间。
涉及员工信息和预算，但原型不发送真实通知、不发放真实权益。
请先给出页面规划和风险建议，不要制作页面。
```

确认后：

```text
规划确认。制作关怀计划列表、四步创建流程、高级详情和关怀模板卡片。
重点验证每一步必填校验、预算确认、失败通知重试和详情三列信息布局。
```

## 11. 交付检查清单

产品经理可以使用以下清单完成原型验收：

### 业务范围

- [ ] 应用、菜单和页面范围与规划一致。
- [ ] 核心角色和权限已说明。
- [ ] 业务对象、字段和状态没有关键遗漏。
- [ ] 高风险操作已明确影响和确认方式。

### 核心流程

- [ ] 默认页面正确。
- [ ] 查询、新增、详情、编辑和返回流程可完成。
- [ ] 状态变化和可执行操作一致。
- [ ] 表单必填、格式和联动符合要求。
- [ ] 模拟行为与真实行为边界清晰。

### 页面规范

- [ ] 应用菜单不超过两级。
- [ ] 列表查询和操作布局符合规范。
- [ ] 主操作在按钮组左侧。
- [ ] 详情、卡片、弹窗和高级表单符合对应规范。
- [ ] 空数据、失败、禁用和加载状态能够理解。

### 验证结果

- [ ] Skill 和配置校验通过。
- [ ] TypeScript 和生产构建通过。
- [ ] 浏览器主流程验证通过。
- [ ] 已记录非阻塞警告和待确认事项。

完成以上检查后，原型可以进入业务评审、视觉细化或接口设计阶段。
